Strategy
Why the layer picker, why now?
The layer picker is the front door to everything CivilGrid's data catalog can offer. Fix the front door and every downstream metric improves.
Activation
New users can't find value
Without role defaults or geography filtering, a new user lands on a wall of 150+ datasets with no starting point. Time-to-first-value is too long. Trials end before the product proves itself.
Retention
Existing users repeat wasted setup
Layer state resets every session. Every returning user re-configures the same map they built last week. This friction is invisible in aggregate but real in every session.
Expansion
The upsell has no UI home
Proprietary layer upload — the planned premium capability — needs a UI paradigm to live in. The layer picker is that foundation. Ship it now; the upsell slots in without re-architecture.
Sales
Demos don't land on day one
A generic layer list in a demo doesn't prove relevance. A geography-aware panel configured for a prospect's exact project state and role does. The layer picker is a sales tool.

Business KPIs
What this feature should move
Not DAU/MAU — this is project-based B2B software. Engineers don't open CivilGrid daily. We measure value per project session and business-level stickiness.
Feature-Level KPIs
Time to First Meaningful Layer Config
How long until a new user reaches a layer state that reflects their actual use case. Role defaults should compress this significantly.
Layer Engagement Depth per Session
Avg distinct layers interacted per session, by role. Breadth of exploration = data catalog value realized.
Layer Config Retention Rate
% of returning users whose saved state is intact on next project open. Confirms persistence is valued.
Business-Level KPIs
Net Revenue Retention (NRR)
Confusing map → high time-to-value per project
↓
Product feels less capable than it is
↓

↓

Trial-to-Paid Conversion
Geography-aware demo shows a prospect their exact project state in 30 seconds. Shortens the "prove you're relevant" phase.
Expansion Revenue (Proprietary Layers)
Layer picker establishes the UI pattern. When custom upload ships, adoption is near-zero learning curve.

Discovery
What I'd want to know first
Before finalizing any design, four evidence streams would shape the solution — or change it entirely.
Usage Analytics
Which layers are active in 80% of sessions? If 12 layers do the heavy lifting across all users, defaults are obvious and role segmentation may be simpler than assumed.
Would inform: default layer sets
5–8 Customer Interviews
"Walk me through your last due diligence session, start to finish." Listen for confusion, repetition, and workarounds — not feature wishlists. Behavior > stated preference.
Would inform: persistence vs. search priority
Support Ticket Analysis
Map configuration complaints, "I can't find X layer" requests, and "why is this showing in [wrong state]" tickets reveal what's actually causing pain at scale.
Would inform: MVP scope prioritization
Sales Call Recordings
Where does the map experience cause friction or enthusiasm in demos? Which layers do prospects ask about that aren't surfaced? Sales signals reveal unmet demand.
Would inform: demo script + Coming Soon roadmap

MVP Scope
What's in. What's out. Why.
In MVP
✓
Hierarchical panel — category → subcategory → layer
✓
Geography-aware filtering — layers shown only if they have coverage in the project state
✓
Three layer states — Active, Available, Coming Soon (with interest signal)
✓
Role-based defaults — Infrastructure Developer / Civil Engineer / Environmental Consultant
✓
Per-project persistence — layer state saves server-side per project, not session
✓
Layer metadata on hover — source, last updated, coverage
✓
Keyword search — real-time filter within the panel
Explicitly Out
✗
Named presets — defer until usage data confirms cross-project reuse
✗
Team/org sharing — requires org data model, separate scope
✗
Proprietary layer upload — separate product build; MVP must not block it
✗
Layer z-index / opacity controls — power user feature, validate demand first
✗
ML recommendations — need usage baseline before training signal exists
Engineering constraint
Layer state must be saved server-side per project — not localStorage. Layer coverage matrix must be updatable by Data team without a code deploy. These are architectural decisions, not UI decisions. Flag for eng scoping early.

Why this sequence?
Each iteration validates the usage pattern needed to justify the next. Presets only make sense once we confirm per-project state is valued. Team sharing only makes sense once preset creation is high. Proprietary upload only converts if users already have a habit of managing layers.
Trigger for each iteration
→
Iter 1: users reconfiguring layers when starting similar projects
→
Iter 2: preset creation high + requests for cross-team consistency
→
Premium: team sharing active + enterprise sales requesting custom data

Go-to-Market
Launch carefully. Let the product talk.
Customer Rollout
Phase 1 — Private Beta
Weeks 1–4
8–12 power users from top accounts who have flagged layer friction. Loom + 30-min onboarding call. Goal: surface geography filtering bugs and wrong role defaults before broad rollout.
Phase 2 — Expanded Beta
Weeks 5–8
Open to active accounts (5+ sessions / 90 days). CS email — not marketing. In-app tooltip sequence: 3 key behaviors, dismissible. Collect structured NPS feedback.
Phase 3 — General Availability
Week 9+
Two-sentence modal on next login. Plain-text email from CEO or Head of Product — not a newsletter. No press release.
Sales Enablement
Updated Demo Path
Rep inputs prospect's actual project location + role. Panel loads geography-filtered + role-appropriate in real time. This is the moment: "here's CivilGrid for your Phoenix project" before showing any data.
One-Liner
"CivilGrid surfaces only the data relevant to your project — filtered by geography, configured for your role — so your team spends time on analysis, not managing the map."
